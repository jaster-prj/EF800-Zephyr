# EF800 Behavior-to-Code/Test Evidence Map

Baseline reviewed: current OpenSpec capabilities and scenario ranges, EF800 CMake/Twister test composition, `docs/migration-status.md`, and the repository development/hardware gates. This map groups closely related scenarios but names each governing capability so refactoring increments can select the exact scenarios they affect. A native test proves only the behavior it exercises; it does not satisfy a capability's separate target/hardware qualification requirement.

## Cross-capability scenario evidence index

Current implementation refresh (2026-11-12): the keyboard application now
composes `keyboard_matrix.c`, `keyboard_i2c_service.c`, and shared
`keyboard_matrix_debounce.c`; the keyboard bootloader composes
`keyboard_boot_handoff.c`; the L496 bootloader composes `boot_handoff.c`.
These modules retain the behavior/test/hardware evidence boundaries shown
above. The current migration snapshot is 178/178 native cases across 26
configurations; see `docs/migration-status.md` for the current image sizes and
explicitly unrun hardware gates. The row's 174-case count is its earlier
baseline, not current status.

## Material gaps to carry into refactoring

1. **Exact source/behavior coverage is not identical to test names.** Several important EF800 Application behaviors are tested in the shared `regression` translation unit and conditional domain test configs. Each increment must verify the relevant CMake/test configuration actually compiles the claimed tests.
2. **Boot update test completeness is unconfirmed for all prohibited targets.** Existing tests explicitly cover bad CRC and truncation; inspect marker/preservation assertions and add only if wrong-target/backup/boot non-modification or failure cleanup is not already meaningfully protected.
3. **Target-only evidence remains open.** No native test can close the documented L496 MPU/fault/recovery, L431 reset/vector/flash, physical MTP/USB, QSPI geometry, or fitted peripheral gates. These must stay listed as hardware acceptance, not refactor-created test tasks.
4. **Physical MTP acceptance has a concrete availability issue.** Migration status reports no raw MTP device in a recent session; it is not evidence of successful host interoperability.
5. **Some native-sim requirements are capabilities of adjacent simulator/web code rather than the six firmware images.** Their C/JS/Python/browser implementation is not in scope for C firmware restructuring; shared EF800 C adapters used by EF800 Application remain subject to the owned-source inventory.
